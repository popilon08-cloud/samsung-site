הוספת IPv4: בנגלור כ-Dual-Stack

עד כאן בנגלור עבדה רק ב-IPv6, וכל שאר הרשת, כלומר חמישה סניפים, רשת המעבר והספקים, עובדת רק ב-IPv4. שני הפרוטוקולים לא מדברים זה עם זה: מחשב בבנגלור לא יכול לשלוח חבילה לשרת בסוון, כי אין לו כתובת IPv4 לשלוח ממנה. כדי שכל הרשת תתקשר היה צריך לגשר על הפער הזה. היו שלוש דרכים:

  • להוסיף IPv6 לכל שאר הרשת. זה שינוי של עשרות נתבים ומתגים, ובנתבי Router-PT הישנים אין בכלל תמיכה ב-IPv6.
  • לתרגם בין הפרוטוקולים (NAT64). ‏Packet Tracer לא תומך בזה.
  • Dual-Stack: להפעיל בבנגלור את שני הפרוטוקולים זה לצד זה. כל רכיב מקבל גם כתובת IPv4 וגם כתובת IPv6, ובוחר בפרוטוקול לפי היעד.

בחרתי ב-Dual-Stack. זו גם השיטה שבה ארגונים עוברים ל-IPv6 במציאות: לא מחליפים פרוטוקול ביום אחד, אלא מריצים את שניהם יחד לאורך שנים. כל מה שהוגדר ב-IPv6 נשאר בדיוק כמו שהיה, ולידו הוספתי IPv4.

תוכנית הכתובות

סוון קיבל את 172.16.0.0/16 וסן חוזה את 172.17.0.0/16. את 172.18.0.0/16 שמרתי לחוות השרתים בהוואסונג, ולכן בנגלור קיבל את 172.19.0.0/16. השיטה זהה לשאר הסניפים: המספר השלישי בכתובת הוא מספר ה-VLAN, והשער הוא ‎.1.

ההגדרה צעד אחר צעד

  1. ב-MLS-SRV: מפעילים ניתוב IPv4 עם ip routing, נותנים ל-SVI של VLAN 10 את הכתובת 172.19.10.1, ומוסיפים נתיב Default אל R-1 ‏(172.19.10.2).
  2. ב-R-1: מוסיפים ip address לכל תת-ממשק, לצד כתובת ה-IPv6 שכבר קיימת בו.
  3. ב-R-1: יוצרים מאגר DHCP לכל מחלקה, ומוציאים מהחלוקה את עשר הכתובות הראשונות עם ip dhcp excluded-address.
  4. ב-R-1: כותבים ACL של IPv4 לכל מחלקה, עם אותה מדיניות של ה-ACL ב-IPv6, ומצמידים אותו עם ip access-group.
  5. ב-R-1: מגדירים NAT: ‏access-list 110, ‏ip nat inside בתתי-הממשקים, ‏ip nat outside בקו לספק, ושורת ה-overload.
  6. ב-R-1: נתיב Default לספק, נתיב לכל הבלוק 172.19.0.0/16 אל Null0, ופקודת network ב-BGP שמפרסמת את הבלוק לספק.
  7. ב-R-2: כתובת ב-VLAN 10, אותו NAT ואותו BGP, ונתיב לבלוק דרך R-1. כך יש לסניף יציאה שנייה.
  8. בחמשת השרתים: Desktop, ואז IP Configuration. ממלאים כתובת, מסכה, שער ו-DNS של IPv4, ולא נוגעים בשדות של IPv6.
  9. בשרת ה-DHCP: בלשונית Services, תחת DHCP, מגדירים את המאגר של VLAN 10 ומפעילים את השירות.
  10. בכל מחשב: Desktop, ואז IP Configuration, ומסמנים DHCP בחלק של IPv4.
  11. בשלושת רכיבי שכבה 3: ‏access-list 10 על קווי ה-VTY, כדי ש-SSH ב-IPv4 יתאפשר רק מרשת השרתים.
  12. בשלושתם: ntp server ו-logging אל 172.19.10.11.
  13. בדיקות, ואז write memory בכל רכיב ושמירת הקובץ.

MLS-SRV

ב-IPv6 ה-MLS כבר ניתב, עם ipv6 unicast-routing. ב-IPv4 צריך להפעיל את הניתוב בנפרד עם ip routing, אחרת המתג מתנהג כמו מתג שכבה 2 ולא מעביר חבילות בין רשתות.

ip routing
interface Vlan10
 ip address 172.19.10.1 255.255.255.0
ip route 0.0.0.0 0.0.0.0 172.19.10.2

R-1: כתובות, ‏DHCP ו-ACL

בכל תת-ממשק יש עכשיו שתי כתובות, אחת מכל פרוטוקול. זה כל הרעיון של Dual-Stack: אותו ממשק, אותו VLAN, שני פרוטוקולים.

interface GigabitEthernet0/0/0.20
 description DEV-GW
 encapsulation dot1Q 20
 ip address 172.19.20.1 255.255.255.0
 ip access-group DEV-IN4 in
 ip nat inside
 ipv6 traffic-filter DEV-IN in
 ipv6 address FE80::1 link-local
 ipv6 address 2001:DB8:3:20::1/64
 ipv6 dhcp server BLR-DEV
! ... .30, .40, .50 (and .10: ip address 172.19.10.2)
!
ip dhcp excluded-address 172.19.20.1 172.19.20.10
ip dhcp pool BLR-DEV-V4
 network 172.19.20.0 255.255.255.0
 default-router 172.19.20.1
 dns-server 172.19.10.11
 domain-name samsung-blr.com
! ... BLR-MOB-V4, BLR-NET-V4, BLR-AI-V4
!
ip access-list extended DEV-IN4
 deny ip 172.19.20.0 0.0.0.255 172.19.30.0 0.0.0.255
 deny ip 172.19.20.0 0.0.0.255 172.19.40.0 0.0.0.255
 deny ip 172.19.20.0 0.0.0.255 172.19.50.0 0.0.0.255
 permit ip any any
! ... MOB-IN4, NET-IN4, AI-IN4

ה-ACL של IPv4 נחוץ: בלעדיו מחלקה שחסומה ב-IPv6 הייתה עוקפת את החסימה דרך IPv4. ב-Dual-Stack כל מדיניות אבטחה צריכה להיכתב פעמיים, פעם לכל פרוטוקול. ל-ACL החדשים נתתי את אותם שמות, עם הסיומת 4.
