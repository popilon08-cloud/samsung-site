VTP ו-Root Guard

בפרק הקודם הגדרתי STP, ‏PortFast ו-BPDU Guard בכל הסניפים. נשארו שתי דרישות של מיתוג מתקדם: VTP, שמפיץ את רשימת ה-VLAN מהמתג המרכזי לשאר המתגים, ו-Root Guard, שמגן על בחירת השורש של ה-STP. הגדרתי את שניהם בסניף תל אביב: MLS אחד וארבעה מתגי גישה, אחד לכל קומה.

VTP: הפצת VLAN בין המתגים

הבעיה

בלי VTP, כל VLAN צריך להגדיר ידנית בכל מתג. בתל אביב יש חמישה מתגים ושבעה VLAN, כלומר 35 הגדרות. אם שוכחים VLAN במתג אחד, המחשבים במתג הזה לא יכולים להיות ב-VLAN הזה, ותעבורה של ה-VLAN לא עוברת ב-Trunk. כל שינוי, כמו הוספת מחלקה, מחייב לעבור על כל המתגים.

מה זה VTP ואיך הוא עובד

VTP ‏(VLAN Trunking Protocol) הוא פרוטוקול של Cisco שמפיץ את מאגר ה-VLAN (המספרים והשמות) בין מתגים, דרך קווי ה-Trunk. מגדירים VLAN פעם אחת במתג אחד, וכל שאר המתגים לומדים אותו לבד. VTP מעביר רק את רשימת ה-VLAN, ולא את השיוך של הפורטים: איזה פורט שייך לאיזה VLAN נשאר הגדרה מקומית בכל מתג.

שלושה דברים חייבים להיות זהים בכל המתגים כדי שהעדכונים יתקבלו:

  • Domain: שם הקבוצה. מתג מקבל עדכונים רק מאותו Domain. בפרויקט: SAMSUNG-TLV.
  • Password: סיסמה שממנה מחושב קוד (MD5) שמצורף לכל עדכון. מתג זר בלי הסיסמה לא יכול לשנות את רשימת ה-VLAN.
  • Version: הגרסה. הגדרתי גרסה 2, שתומכת בכל סוגי ה-VLAN ומעבירה עדכונים גם דרך מתג Transparent.

הסכנה: Configuration Revision

כל שינוי ב-VLAN מעלה ב-1 מספר שנקרא Configuration Revision. מתג שמקבל עדכון עם מספר גבוה מזה שלו מחליף את כל רשימת ה-VLAN שלו ברשימה שקיבל, גם אם הוא Server. זו הטעות המפורסמת של VTP: מחברים לרשת מתג ישן ממעבדה, עם אותו Domain ומספר Revision גבוה, והוא מוחק את כל ה-VLAN בחברה. המחשבים מאבדים את ה-VLAN שלהם והרשת נופלת.

כדי למנוע את זה, לפני שמכניסים מתג ל-Domain מאפסים לו את ה-Revision ל-0. שתי דרכים מאפסות: מעבר למצב Transparent, ושינוי שם ה-Domain. בהגדרה שלמטה כל מתג גישה עובר קודם ל-Transparent, ורק אחר כך ל-Client. בנוסף, הסיסמה מונעת ממתג זר להשתתף בכלל.

Root Guard: הגנה על השורש של STP

ב-STP השורש נבחר לפי העדיפות הנמוכה ביותר. בתל אביב ה-MLS הוא השורש, עם עדיפות 24576. אם מישהו מחבר מתג עם עדיפות נמוכה יותר (למשל 0), המתג הזה הופך לשורש, וכל התעבורה בסניף מתחילה לזרום דרכו. זו גם התקפה: התוקף רואה את כל התעבורה, ויכול לגרום לחישוב מחדש של העץ בכל פעם שהוא מתנתק ומתחבר.

Root Guard מוגדר על פורט שאסור שיגיע ממנו שורש, כלומר הפורטים שהשורש מחזיק לכיוון מטה. אם בפורט כזה מגיעה הודעת BPDU טובה יותר מזו של השורש הנוכחי, המתג לא משנה את השורש: הוא חוסם את הפורט ומסמן אותו כ-root-inconsistent. כשההודעות הטובות מפסיקות להגיע, הפורט חוזר לעבוד לבד.

ההגדרה צעד אחר צעד

הסדר חשוב: קודם ה-Server, אחר כך כל Client בנפרד, ובסוף בדיקה. כך מתג גישה אף פעם לא נמצא באותו Domain עם Revision גבוה מזה של ה-MLS.

שלב 1: ה-MLS (Server) ו-Root Guard

לפני שמתחילים, בודקים ש-VLAN 999 (פורטים לא בשימוש) קיים גם ב-MLS. ה-MLS הוא מקור הרשימה, ו-VLAN שלא קיים בו יימחק בסוף ממתגי הגישה.

ISR_Samsung_F1-MLS# show vlan brief          ! check that 10-50 and 999 exist
ISR_Samsung_F1-MLS# configure terminal
ISR_Samsung_F1-MLS(config)# vtp mode server
ISR_Samsung_F1-MLS(config)# vtp domain SAMSUNG-TLV
ISR_Samsung_F1-MLS(config)# vtp password Samsung-TLV-Vtp
ISR_Samsung_F1-MLS(config)# vtp version 2
ISR_Samsung_F1-MLS(config)# spanning-tree vlan 1,999 priority 24576
ISR_Samsung_F1-MLS(config)# interface range GigabitEthernet1/0/2 - 5
ISR_Samsung_F1-MLS(config-if-range)# spanning-tree guard root
ISR_Samsung_F1-MLS(config-if-range)# end
ISR_Samsung_F1-MLS# write memory
ISR_Samsung_F1-MLS# show vtp status

שינוי ה-Domain איפס את ה-Revision ל-0, והפקודה הבאה העלתה אותו ל-1. הפקודה spanning-tree vlan 1,999 priority 24576 משלימה את השורש גם ל-VLAN 1 ו-999. ל-VLAN 10–50 הוא כבר היה מוגדר. בלי זה, Root Guard יכול לחסום את הפורטים ב-VLAN שבו ה-MLS לא הוגדר כשורש (ראו בבדיקה).

ה-MLS אחרי ההגדרה: ‏Server, ‏Domain SAMSUNG-TLV, גרסה 2, ‏Revision 1

שלב 2: כל מתג גישה (Client)

אותן פקודות בכל אחד מארבעת מתגי הגישה. השורה vtp mode transparent מאפסת את ה-Revision לפני שהמתג נכנס ל-Domain, ורק אחריה המתג עובר ל-Client:

ISR_Samsung_F3-SALES# configure terminal
ISR_Samsung_F3-SALES(config)# vtp mode transparent     ! resets the revision to 0
ISR_Samsung_F3-SALES(config)# vtp domain SAMSUNG-TLV
ISR_Samsung_F3-SALES(config)# vtp password Samsung-TLV-Vtp
ISR_Samsung_F3-SALES(config)# vtp version 2
ISR_Samsung_F3-SALES(config)# vtp mode client
ISR_Samsung_F3-SALES(config)# end
ISR_Samsung_F3-SALES# write memory
ISR_Samsung_F3-SALES# show vtp status

שלב 3: שמירת הקובץ

אחרי ארבעת המתגים שמרתי את קובץ ה-Packet Tracer (File ← Save) לפני הבדיקות.

בדיקה: VTP מפיץ VLAN חדש

כדי לבדוק שה-VTP עובד, יצרתי ב-MLS ‏VLAN בדיקה, 60 בשם VTP-TEST, ובדקתי אם מתג גישה לומד אותו בלי שהגדרתי אותו בו:

ISR_Samsung_F1-MLS(config)# vlan 60
ISR_Samsung_F1-MLS(config-vlan)# name VTP-TEST
ISR_Samsung_F1-MLS(config-vlan)# end

במתג SALES הופיע VLAN 60 בשם VTP-TEST. ה-Revision עלה ל-3, והשדה Configuration last modified by מראה 192.168.10.1, כלומר העדכון הגיע מה-MLS. השיוך של הפורטים במתג לא השתנה: Fa0/1–8 נשארו ב-VLAN 20, והפורטים הפנויים ב-999.

מתג SALES: ‏Client, ‏Revision 3, והעדכון האחרון הגיע מ-192.168.10.1 (ה-MLS)

מתג SALES: ‏VLAN 60 ‏(VTP-TEST) נלמד מה-MLS, והפורטים נשארו ב-VLAN שלהם

בדיקה: Root Guard חוסם שורש זר

הבדיקה של VTP הראתה גם את Root Guard בפעולה, בלי שתכננתי. ב-VLAN 60 החדש לא הוגדרה ל-MLS עדיפות שורש, ולכן הוא היה בעדיפות ברירת המחדל 32768, כמו כל שאר המתגים. במצב כזה השורש נבחר לפי כתובת ה-MAC, ומתג הגישה בפורט Gi1/0/2 היה זוכה. זה בדיוק המצב ש-Root Guard נועד לעצור: מתג גישה שמנסה להפוך לשורש.

ה-MLS הציג מיד את ההודעה ROOTGUARDBLOCK: Port 1/0/2 tried to become non-designated in VLAN 60, והעביר את הפורט למצב root-inconsistent. ב-show spanning-tree vlan 60 ה-MLS נשאר השורש (This bridge is the root), והפורט Gi1/0/2 מופיע במצב BLK רק ב-VLAN הזה. בשאר ה-VLAN אותו פורט המשיך לעבוד כרגיל:

ה-MLS: יצירת VLAN 60, ארבע שורות spanning-tree guard root, והודעת ROOTGUARDBLOCK על Gi1/0/2

הודעת Root Guard: הפורט הועבר ל-root-inconsistent ב-VLAN 60

ב-VLAN 60 ה-MLS נשאר השורש, והפורט Gi1/0/2 חסום (BLK)

אחרי הבדיקה מחקתי את VLAN 60 ב-MLS (no vlan 60). גם המחיקה עברה ב-VTP: במתג SALES ה-Revision עלה ל-4, ‏VLAN 60 נעלם מהרשימה, ונשארו 11 VLAN, כמו ב-MLS.

מתג SALES אחרי המחיקה: ‏Revision 4, העדכון מ-192.168.10.1, ו-VLAN 60 כבר לא ברשימה

בדיקה אחרי הניקוי

בדקתי ב-show spanning-tree את כל ה-VLAN ב-MLS: בכל אחד מהם ה-MLS הוא השורש, וכל ארבעת הפורטים למתגי הגישה במצב Designated / FWD. ping מה-MLS לשרת ה-Web ‏(192.168.40.11) ולמתג SALES ‏(192.168.40.4) עבר. ה-ping הראשון נכשל בגלל ARP, כרגיל.

ה-MLS אחרי הניקוי: ב-VLAN 40, 50 ו-999 השורש הוא ה-MLS, וכל הפורטים FWD

הערה על show spanning-tree summary: בפקודה הזאת Packet Tracer מציג פורט חסום אחד בכל VLAN, אבל בפירוט המלא של כל VLAN אין אף פורט חסום, וכל ארבעת הפורטים במצב FWD. המונה בסיכום לא תואם לפירוט, ולכן הסתמכתי על show spanning-tree vlan X.

איך מוסיפים VLAN מעכשיו

עם VTP ו-Root Guard, הוספת VLAN בתל אביב נעשית רק ב-MLS, בשתי פקודות. בלי הפקודה השנייה, Root Guard יחסום את ה-VLAN החדש, כמו שקרה ב-VLAN 60:

ISR_Samsung_F1-MLS(config)# vlan 70
ISR_Samsung_F1-MLS(config-vlan)# name NEW-DEPT
ISR_Samsung_F1-MLS(config-vlan)# exit
ISR_Samsung_F1-MLS(config)# spanning-tree vlan 70 priority 24576

אחר כך, בכל מתג גישה מגדירים רק את הפורטים (switchport access vlan 70). את ה-VLAN עצמו אין צורך ליצור, כי הוא כבר הגיע ב-VTP.

סיכום

  • ה-MLS בתל אביב הוא VTP Server, וארבעת מתגי הגישה הם Client באותו Domain, עם סיסמה וגרסה 2. VLAN חדש מוגדר פעם אחת, ב-MLS.
  • כל מתג נכנס ל-Domain דרך מצב Transparent, ולכן אף מתג לא דרס את רשימת ה-VLAN של ה-MLS.
  • Root Guard על ארבעת הפורטים של ה-MLS שומר עליו כשורש. בבדיקה הוא חסם מתג גישה שניסה להפוך לשורש ב-VLAN 60.
  • VTP ו-Root Guard תלויים זה בזה: כל VLAN חדש ב-VTP צריך גם עדיפות שורש ב-MLS.
